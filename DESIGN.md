# Design notes

Everything below was verified against 1.21.11 sources on 2026-07-27 (Fabric API branch `1.21.11`, NeoForge branch `1.21.11` decompile patches, vanilla data via `misode/mcmeta` tag `1.21.11-summary`). Re-verify when bumping Minecraft.

## How surface light works in 1.21.11

The pipeline, from data to gameplay:

1. **Timelines** (datapack registry `timeline`, attached to dimensions through tags — overworld uses `#minecraft:in_overworld` = `day` + `moon` + `early_game` + `universal`). Each timeline animates *environment attribute* tracks with keyframes, easing and a compose modifier (`multiply`, `maximum`, `or`...).
2. **Environment attributes** (registry `environment_attribute`, ~45 entries) — the interesting ones here: `gameplay/sky_light_level`, `visual/sky_light_factor`, `visual/sky_light_color`, `visual/star_brightness`, `visual/moon_angle`, `visual/moon_phase`. Vanilla's `day` timeline drives `gameplay/sky_light_level`: 1.0 by day, 0.26666668 at night (= 4/15), ramping at ticks 133→11867 and 13670→22330.
3. **`Level#skyDarken`** — recomputed each tick by `Level#updateSkyBrightness()` (still present in 1.21.11; called from `ServerLevel`). 0 at noon, 11 at clear-night midnight, weather included.
4. **Effective light** at a position = raw sky light − `skyDarken` (via `getSkyDarken()`), combined with block light. This is what mob spawning (`monster_spawn_light_level`: uniform 0–7 in the overworld `dimension_type`), crops, and daylight sensors read.

So there are two natural places to act, and this mod uses both:
- **data**: add timeline tracks on `gameplay/sky_light_level` (static, composable, survives updates well);
- **code**: `@ModifyReturnValue` on `getSkyDarken()I` (dynamic, downstream of everything — timeline, weather, other mods).

## Advancement layer — design constraints

`skyDarken` is per-`Level`, not per-player. Two coherent shapes:
- **World-global**: "once anyone completes X, nights get brighter" → flip a server-side flag consumed by `LightRules`. Simple, no networking.
- **Per-player**: only possible visually (client side). Server detects the advancement, syncs a `CustomPacketPayload` via `ServerPlayNetworking`, client applies a visual-only effect. Payload pattern to copy: `record ... implements CustomPacketPayload` with a `Type<>` + codec (see `CustomIngredientPayloadC2S` in fabric-api for the current idiom, and https://docs.fabricmc.net/develop/networking).

## Visual layer notes

Mechanical light (above) also changes what you *see* only indirectly. For pure looks:
- `visual/sky_light_factor`, `visual/sky_light_color`, `visual/star_brightness` are timeline-animatable attributes — likely the clean data-driven route (e.g. brighter stars + colder light on full moon). Semantics to confirm in `genSources` (`EnvironmentAttributes` class).
- The lightmap itself is GPU-generated in 1.21.11 (`LightTexture` is a small class; NeoForge no longer patches an update method). Old True-Darkness-style "rewrite lightmap pixels" approaches predate this — prefer the attributes.
- `dimension_type.ambient_light` (0.0 in the overworld) is the data knob for the minimum visual brightness floor.

## Multi-version strategy

- **1.21.9 / 1.21.10 / 1.21.11**: same loader (0.19.3), same Mojang mappings, same template layout; the timeline/attribute system exists since 1.21.9. Supporting all three is likely "widen `minecraft` in `fabric.mod.json` to `>=1.21.9 <=1.21.11`, pin fabric-api per version (0.134.1 / 0.138.4 / 0.141.5), test each". Do it once the mod stabilizes.
- **≤ 1.21.8 and the 26.x line**: different world (yarn mappings before the switch, no timelines before 1.21.9; 26.1+ is a new version scheme with its own template branches). If ever needed, use per-version source with Stonecutter (https://stonecutter.kikugie.dev) rather than one jar.
- Recommendation: stay pinned to `~1.21.11` until the feature set settles.

## Open questions

- Whether weather in 1.21.11 modulates `sky_light_level` via an attribute layer or still via the legacy formula — check `updateSkyBrightness()` in `genSources`.
- `attribute_type` registry contains `moon_phase` — check whether attributes can be keyed on moon phase directly (could replace the 32-keyframe timeline with something terser).
